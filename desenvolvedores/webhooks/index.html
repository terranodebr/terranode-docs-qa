Webhooks¶

Um webhook avisa outro sistema quando algo acontece num projeto, sem que ele precise perguntar à API de tempos em tempos. Você cadastra um endereço HTTPS, e o terranode envia a ele uma mensagem pequena e assinada a cada evento escolhido: um projeto criado, iniciado, concluído, reaberto, alterado ou arquivado, e um lote de coleta aberto, fechado ou completo.

A mensagem diz o que aconteceu e a quê, sem os dados em si. Quem precisa de mais detalhes busca na API com uma chave de API.

Quem pode usar¶

Só o papel Gestor configura webhooks e vê suas entregas: a permissão é webhook:manage. Uma chave de API com o papel Gestor também pode. Veja Papéis e permissões.

Onde configurar¶

  • No web app, em Configurações, na seção Webhooks.
  • Na linha de comando, com tn webhooks. Veja Linha de comando tn.
  • Pela API, nas rotas /api/v1/webhooks. A referência completa está em /api/v1/docs.

Cada webhook tem:

  • um endereço, que precisa usar HTTPS e apontar para um servidor público;
  • uma descrição, opcional;
  • os tipos de evento que ele recebe, ao menos um;
  • os projetos a que ele se limita, opcional. Sem projetos, ele recebe os eventos de todos.

Uma organização pode ter até 20 webhooks.

No web app, Novo webhook abre um assistente em três passos: Destino (endereço e descrição), Eventos e Projetos. Ao lado de cada passo, a Prévia mostra a requisição que o seu sistema vai receber: o POST para o endereço, os cabeçalhos e o corpo JSON do evento. Clique num evento para ver o exemplo dele. Ao escolher um projeto, o exemplo passa a mostrar esse projeto.

Depois de criar, o assistente mostra o segredo e um exemplo de verificação em Python e em Node.js. No exemplo, o segredo vai numa linha do .env, e o código lê essa variável, então o segredo não fica gravado no código. Ao gerar um novo segredo na página do webhook, aparece o mesmo exemplo. Pela API, o exemplo de cada tipo vem no campo example de GET /api/v1/webhooks/event-types.

Eventos¶

Tipo Quando acontece
project.created Um projeto é criado.
project.started Um projeto passa de rascunho para em andamento, ou é criado em andamento.
project.finished Um projeto é concluído.
project.reopened Um projeto concluído é reaberto.
project.updated Um salvamento altera campos, área, formulários, camadas ou equipe do projeto.
project.archived Um projeto é arquivado.
batch.opened Um dispositivo abre um lote de coleta.
batch.closed Um dispositivo fecha um lote, declarando quantas respostas e mídias vai enviar.
batch.completed Tudo o que um lote declarou chegou ao servidor.

Algumas regras valem para todos:

  • Um salvamento gera um único project.updated, com a lista do que mudou, mesmo que tenha alterado o nome e a equipe de uma vez.
  • Mudanças de status têm eventos próprios e não aparecem no project.updated. Reabrir um projeto com um novo prazo envia um project.reopened e um project.updated com o prazo.
  • A criação de um projeto não envia project.updated, mesmo que ele já nasça com equipe, formulários e camadas.
  • Coletas não geram um webhook cada. Elas chegam agrupadas no lote: o batch.closed diz quantas o celular declarou, e o batch.completed confirma que todas estão no servidor.
  • A nova revisão de um formulário não altera os projetos que o usam, e não envia nada.

A mensagem¶

Cada entrega é um POST com um corpo JSON assim:

{
  "type": "batch.completed",
  "timestamp": "2026-11-04T13:20:00+00:00",
  "data": {
    "organization": {"id": "0193f000-...-0001", "slug": "acme"},
    "project": {"id": "0193f000-...-0002", "slug": "obra-br101"},
    "subject": {"type": "batch", "id": "0193f000-...-0003"},
    "batch": {
      "sequence": 12,
      "collector_id": "0193f000-...-0004",
      "device_id": "0193f000-...-0005"
    },
    "counts": {"responses": 41, "media": 130}
  }
}
  • timestamp é quando o evento aconteceu.
  • subject diz do que o evento trata: o projeto, ou o lote nos eventos batch.*.
  • project.created traz também status, o status em que o projeto foi criado.
  • project.updated traz changes, a lista do que mudou. Os nomes possíveis são name, slug, description, kind, estimated_deadline, requires_review, encrypted, area, surveys, layers e members.
  • batch.closed e batch.completed trazem counts, com o número de respostas e de mídias do lote.

A mensagem nunca leva respostas coletadas, mídias, geometrias nem o texto da descrição do projeto. Para buscar as respostas que um lote trouxe, filtre a listagem de respostas do projeto pelo lote:

curl -H "Authorization: Bearer $TN_TOKEN" -H "X-Organization: acme" \
  "https://app.terranode.com.br/api/v1/projects/obra-br101/responses?batch=0193f000-...-0003"

Novos campos e novos tipos podem aparecer com o tempo. O significado de um campo existente não muda: uma mudança incompatível viria como um tipo novo. Ignore campos que você não conhece.

Verificar a assinatura¶

As entregas seguem a especificação aberta Standard Webhooks. Cada requisição traz três cabeçalhos:

Cabeçalho Conteúdo
webhook-id O id da mensagem. É o mesmo em todas as tentativas e reenvios.
webhook-timestamp O horário da tentativa, em segundos Unix.
webhook-signature v1, seguido do HMAC-SHA256, em base64, de {id}.{timestamp}.{corpo}.

O segredo do webhook começa com whsec_ e aparece uma única vez, quando você cria o webhook ou troca o segredo. Guarde-o num cofre.

A forma mais simples de verificar é usar uma biblioteca da especificação, que existe para várias linguagens. Em Python:

import os
from standardwebhooks.webhooks import Webhook

webhook = Webhook(os.environ["TERRANODE_WEBHOOK_SECRET"])  # "whsec_..."
mensagem = webhook.verify(corpo_bruto, cabecalhos)  # levanta exceção se for inválida

Em Node.js:

import { Webhook } from "standardwebhooks";

const webhook = new Webhook(process.env.TERRANODE_WEBHOOK_SECRET);
const mensagem = webhook.verify(corpoBruto, cabecalhos);

Verifique sempre o corpo bruto, como chegou, antes de convertê-lo de JSON. A biblioteca também recusa um webhook-timestamp muito antigo, o que impede que uma requisição capturada seja reenviada depois.

Ao trocar o segredo, o anterior continua assinando por 24 horas. Nesse período o webhook-signature traz duas assinaturas separadas por espaço, e a biblioteca aceita qualquer uma delas. Assim você tem tempo de atualizar o seu sistema.

Entrega e novas tentativas¶

Uma entrega dá certo quando o seu servidor responde com um status 2xx em até 10 segundos. Qualquer outra resposta, um redirecionamento, um tempo esgotado ou uma falha de conexão conta como falha.

Depois de uma falha, o terranode tenta de novo após cerca de 1 minuto, 5 minutos e 30 minutos. A entrega é dada como falha depois da quarta tentativa, cerca de 40 minutos depois da primeira.

Duas consequências para quem recebe:

  • A mesma mensagem pode chegar mais de uma vez. Por exemplo, quando o seu servidor processou a mensagem mas demorou a responder. Use o webhook-id para descartar repetições.
  • A ordem não é garantida. Um batch.completed pode chegar antes do batch.closed do mesmo lote. Use o timestamp quando a ordem importar.

Responda rápido e deixe o processamento pesado para depois: guarde a mensagem, responda 200 e trate-a em segundo plano.

Pausa automática¶

Quando cinco entregas seguidas de um webhook falham depois de todas as tentativas, o webhook é pausado e os Gestores da organização recebem um e-mail. Um webhook pausado não recebe nada, e o que aconteceu durante a pausa não é enviado depois. As entregas que ainda aguardavam uma nova tentativa no momento da pausa são dadas como falha; dá para reenviá-las depois. Corrija o endereço e retome o webhook em Configurações ou com tn webhooks resume.

Você também pode pausar um webhook de propósito, por exemplo durante uma manutenção do seu sistema.

Testar e reenviar¶

  • Testar envia uma mensagem do tipo ping, mesmo a um webhook pausado. Ela aparece entre as entregas, com a resposta do seu servidor.
  • Reenviar cria uma nova entrega de uma mensagem que já foi enviada, com o mesmo webhook-id.
  • O histórico de entregas mostra cada tentativa, com o status HTTP, o erro e o começo da resposta. Entregas e mensagens ficam guardadas por 30 dias.

Segurança¶

  • O endereço precisa usar HTTPS e não pode ter usuário e senha.
  • O terranode nunca entrega a endereços internos: redes privadas, o próprio servidor, endereços de metadados de nuvem. O nome do servidor é conferido a cada tentativa, não só no cadastro.
  • Redirecionamentos não são seguidos.
  • Confira a assinatura de toda mensagem antes de agir sobre ela.
