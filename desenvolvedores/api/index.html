API e SDK¶

A API é a forma de ligar o terranode aos outros sistemas da organização: alimentar catálogos a partir de um ETL, consultar o que foi coletado, administrar membros a partir de outro cadastro. É a mesma API que o web app, o aplicativo e a linha de comando usam.

Tudo o que o web app, o aplicativo de campo e a linha de comando tn fazem passa pela API pública do terranode. Esta página explica o que você precisa para chamá-la de um script, de uma integração ou de outro sistema, e apresenta o SDK Python terranode-client.

Quem pode usar¶

Qualquer membro com e-mail verificado pode obter um token e chamar a API. O que cada chamada exige depende do papel do membro, ou do papel da chave de API, na organização: a matriz está em Papéis e permissões. Criar chaves de API, listar e revogar dispositivos são ações só de Gestor.

Endereço e documentação¶

A API vive em /api/v1 no mesmo endereço do web app. A documentação interativa (OpenAPI) fica em /api/v1/docs, e o esquema em /api/v1/openapi.json. Lá estão todas as rotas, campos e respostas; esta página cobre só as convenções que valem para todas elas.

As rotas estão agrupadas por recurso: /auth (login, identidade, chaves de API, dispositivos), /organizations (membros e convites), /catalogs (catálogos, estilos, fontes de dados, envios), /surveys (formulários e modelos), /projects (projetos, equipe, camadas, formulários, pacotes, eventos, coletas), /integrations, /search e /settings.

Equipe, camadas e formulários de um projeto podem ser salvos de uma vez, com PATCH /projects/{projeto} e a lista completa, ou alterados um a um: POST/PATCH/DELETE /projects/{projeto}/members, POST/DELETE /projects/{projeto}/layers e POST/DELETE /projects/{projeto}/surveys. As rotas de um item só mexem nele e deixam o resto do projeto como está.

Nos filtros de pessoa do projeto (people nos eventos, collector nas coletas e nas séries da visão geral), a pessoa pode ser indicada pelo id do usuário ou pelo e-mail, inclusive alguém que já saiu da organização. Um e-mail que nenhum membro tem recebe 404.

Autenticação¶

Toda chamada leva um token no header Authorization:

Authorization: Bearer <token>

Há dois tipos de token, e a API trata os dois do mesmo jeito:

Token Como obter Validade
Token de login POST /api/v1/auth/login com email e password 30 dias
Chave de API POST /api/v1/auth/api-keys ou tn orgs api-keys create 365 dias por padrão, até 3650, ou sem validade

O login devolve access_token, expires_at e o perfil do usuário. Um token de login é pessoal e carrega o seu papel; redefinir a senha revoga todos os tokens da conta. Para scripts e servidores, use uma chave de API: ela tem o próprio papel, não depende de uma pessoa e não precisa do header de organização. Como criar, listar e revogar chaves está em Chaves de API e dispositivos.

GET /api/v1/auth/me mostra quem é o token atual, suas organizações e as permissões em cada uma. Um token expirado ou revogado recebe 401.

Organização¶

Cada chamada acontece dentro de uma organização, informada pelo header X-Organization com o id ou o slug:

X-Organization: acme

O header é opcional quando o token pertence a uma só organização (uma chave de API sempre pertence a uma só). Sem ele, um token com várias organizações recebe 400 com "X-Organization is required.". Uma organização da qual o token não é membro recebe 403, e um membro com e-mail não verificado recebe 403 com a instrução de confirmar o e-mail.

Refs: id ou slug¶

Nos caminhos da API, um segmento que identifica organização, catálogo, fonte de dados ou projeto aceita tanto o id (UUID) quanto o slug, resolvido dentro da organização ou do recurso pai. Envios, chaves de API, membros, convites, dispositivos, camadas de projeto e pacotes não têm slug e são sempre identificados pelo id. Slugs podem mudar quando alguém renomeia o recurso; em integrações duradouras, guarde ids.

Duas exceções nas rotas de projeto: um membro da equipe é indicado pelo id do usuário ou pelo e-mail, e uma camada é removida pelo catálogo e pela fonte de dados que ela desenha (com o nome só para escolher entre duas camadas da mesma fonte).

Paginação¶

Toda listagem (GET de uma coleção) devolve o mesmo envelope:

{"count": 342, "limit": 100, "offset": 0, "results": [ ... ]}
Parâmetro Padrão Regra
limit 100 Máximo 100; um valor maior é reduzido para 100
offset 0 Quantos itens pular

limit igual ou menor que zero e offset negativo devolvem 400. Para percorrer tudo, some o tamanho de cada página ao offset até alcançar count. A exceção é /search, que devolve uma lista simples com os melhores resultados (até 50).

Erros¶

Erros voltam com o status HTTP adequado e um corpo JSON com detail:

{"detail": "You do not have access to this organization."}
Status Quando
400 Dado inválido ou header obrigatório ausente
401 Token ausente, expirado ou revogado
403 Sem permissão, ou e-mail não verificado
404 Recurso inexistente, ou fora da organização atual
409 Ação recusada por uma regra; traz também code, um identificador estável do motivo
422 Corpo da requisição não bate com o esquema; detail é uma lista de problemas

Erros de esquema de formulário (400) trazem ainda errors, uma lista de {pointer, message} apontando o campo com problema.

SDK Python: terranode-client¶

terranode-client é a biblioteca Python por trás do tn. Ela cobre autenticação, identidade, membros, convites, chaves de API, dispositivos, catálogos, fontes de dados e envios. Projetos, formulários, integrações e busca ainda não estão no SDK: para eles, chame a API diretamente.

Ainda não está no pip

Assim como o tn, o SDK ainda não foi publicado em um repositório de pacotes. Peça o acesso ao seu contato no terranode. Requer Python 3.12 ou mais novo.

TerranodeClient() sem argumentos usa a mesma configuração do tn: o arquivo ~/.config/tn/config.json e as variáveis TN_API_URL, TN_TOKEN e TN_ORG, na ordem descrita em Linha de comando tn. Para apontar explicitamente, passe um TerranodeConfig:

from pathlib import Path

from terranode_client import TerranodeClient, TerranodeConfig

config = TerranodeConfig(
    api_url="https://<endereco-da-api>",
    token="<chave de API ou token de login>",
    org="acme",
)

with TerranodeClient(config) as client:
    me = client.me()
    print(me.email, [m.org_slug for m in me.memberships])

    catalog = client.create_catalog(name="Limites de campo", visibility="private")

    upload = client.create_upload(catalog.slug, Path("estradas.geojson"))
    upload = client.wait_for_upload(catalog.slug, upload.id)
    print(upload.status, upload.data_source_slugs)

    for source in client.list_data_sources(catalog.slug):
        print(source.slug, source.geometry_type)

Algumas convenções do SDK:

  • Os métodos de listagem (list_catalogs, list_data_sources, list_uploads, list_members, list_invitations) devolvem iteradores que percorrem todas as páginas sozinhos.
  • create_upload cria o envio e manda o arquivo; wait_for_upload consulta o status a cada 2 segundos por até 5 minutos e lança TimeoutError se o processamento não terminar nesse prazo.
  • Respostas de erro viram exceções tipadas: AuthenticationError (401), PermissionDeniedError (403), NotFoundError (404), ConflictError (409) e ValidationErrorResponse (400 e 422), todas filhas de TerranodeAPIError, com status_code e detail.
  • Os objetos devolvidos (Catalog, DataSource, Upload, User e outros) espelham o JSON da API campo a campo.

OGC API¶

Os dados de um catálogo também podem ser lidos por qualquer ferramenta que fale OGC API Features, como o QGIS, usando o mesmo token Bearer; veja Usar os dados em outras ferramentas.
