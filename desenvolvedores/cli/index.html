Linha de comando tn

Linha de comando tn¶

A linha de comando serve para automatizar o que seria repetitivo no web app, como enviar dezenas de arquivos, convidar uma lista de pessoas ou integrar o terranode a um pipeline. Tudo o que ela faz também pode ser feito pela API.

tn é o cliente de linha de comando do terranode. Com ele você entra na sua conta, administra membros, convites, chaves de API e dispositivos da organização, cria catálogos, envia arquivos e cria e acompanha projetos a partir de um terminal ou de um script. Tudo o que o tn faz passa pela mesma API pública descrita em API e SDK.

Ainda não está no pip

O tn ainda não foi publicado em um repositório de pacotes: pip install não vai encontrá-lo. Peça o acesso ao seu contato no terranode. Ele requer Python 3.12 ou mais novo.

Quem pode usar¶

Qualquer membro da organização pode entrar e consultar a própria identidade. O que cada comando exige depende do papel do membro (ou da chave de API) que está autenticado. A matriz completa está em Papéis e permissões.

Comandos Gestor (owner) Editor (editor) Coletor (field)
auth, config, orgs list, orgs members list sim sim sim
catalogs, datasources, uploads sim sim não
orgs members set-role e remove, orgs invitations sim não não
orgs api-keys, orgs devices sim não não
projects list, get, members list, layers list, surveys list, bundles list, stats, daily, team, events, responses list, summary, get sim sim sim
projects create e archive sim sim não
projects update, start, finish, reopen, bundles retry, members add, set-role e remove, layers add e remove, surveys add e remove criador ou gestor do projeto criador ou gestor do projeto criador ou gestor do projeto
projects responses review gestor ou revisor do projeto gestor ou revisor do projeto gestor ou revisor do projeto

Entrar¶

Depois de instalar, o tn aponta para http://localhost:8000, o endereço de desenvolvimento local. Antes de qualquer outro comando, informe o endereço da API que o terranode passou para você e entre:

tn config set-url https://<endereco-da-api>
tn auth login

O login pede e-mail e senha e guarda um token próprio no arquivo de configuração (veja abaixo). Esse token vale por 30 dias; depois disso o tn responde com um erro de autenticação e basta entrar de novo. Ele é independente da sessão do navegador, mas redefinir a senha encerra todos os tokens da conta, inclusive o do tn (veja Sua conta).

Ao entrar, o tn escolhe a organização sozinho quando você pertence a uma só. Se pertence a várias, ele lista todas e pede que você escolha uma com tn config set-org <org>. tn auth whoami mostra quem você é, suas organizações e o que pode fazer em cada uma. tn auth logout revoga o token no servidor (quando consegue) e sempre o apaga do arquivo local.

Para scripts, pipelines de CI ou servidores, não use sua senha pessoal: crie uma chave de API com tn orgs api-keys create e use-a como token. O que é uma chave, validade e revogação estão em Chaves de API e dispositivos.

Arquivo de configuração e variáveis de ambiente¶

O tn guarda a configuração em ~/.config/tn/config.json (no Linux; em outros sistemas, na pasta de configuração padrão do usuário). O arquivo é criado com permissão só para o seu usuário (modo 0600) e tem três chaves:

Chave O que é Padrão
api_url Endereço da API http://localhost:8000
token Token de login ou chave de API vazio
org Organização padrão (id ou slug) vazio

Cada valor pode vir de três lugares. Quando mais de um está definido, vale o primeiro desta lista:

  1. Flag global na linha de comando: --api-url, --token, --org.
  2. Variável de ambiente: TN_API_URL, TN_TOKEN, TN_ORG.
  3. O arquivo de configuração.

Duas variáveis a mais servem só para tn auth login: TN_EMAIL e TN_PASSWORD dispensam os prompts de e-mail e senha. Para tokens e senhas, prefira variáveis de ambiente às flags, para o segredo não ficar no histórico do shell.

Os comandos tn config editam o arquivo sem passar pelo login:

tn config show                 # mostra api_url e org; o token aparece só como "set"
tn config set-url <url>
tn config set-token            # sem argumento, pede o token sem ecoar
tn config set-org <org>

set-token é o jeito de instalar uma chave de API em outra máquina. Ele tenta resolver a organização como o login faz; se não conseguir (sem rede, token inválido), o token é salvo mesmo assim e você define a organização com set-org.

Flags globais, saída e erros¶

As flags globais vão entre tn e o comando:

Flag Efeito
--json Saída em JSON, com todos os campos, em vez de tabela
--org <ref> Usa outra organização só neste comando
--api-url <url> Usa outro endereço de API só neste comando
--token <token> Usa outro token só neste comando (prefira TN_TOKEN)

Por padrão o tn imprime tabelas com as colunas mais úteis; um recurso único (catálogo, envio, fonte de dados) aparece como lista campo a campo. Com --json a saída traz todos os campos, com datas em ISO 8601, e é a forma indicada para scripts:

tn --json catalogs list

Erros saem em stderr como Error: <mensagem> e o comando termina com código 1. Um erro de autenticação (token ausente, expirado ou revogado) vem com a dica de rodar tn auth login ou definir TN_TOKEN.

tn sem comando mostra a ajuda, e tn <comando> --help mostra a ajuda daquele comando. tn --install-completion instala o autocompletar do seu shell.

Refs: id ou slug¶

Um ref é o valor que você digita para identificar algo. Organizações, catálogos, fontes de dados e projetos aceitam tanto o id (UUID, estável) quanto o slug mostrado nas listagens. Envios, chaves de API e dispositivos não têm slug e são sempre identificados pelo id. Membros e convites são identificados pelo e-mail. Uma coleta é identificada pelo id ou pelo número que aparece no web app, como RDO-DNIT097-00139.

Slugs são mais fáceis de digitar, mas podem mudar quando alguém renomeia o recurso. Em scripts de longa duração, use ids.

Árvore de comandos¶

tn auth         login [--email] [--password] | logout | whoami
tn config       show | set-url <url> | set-token [token] | set-org <org>
tn orgs         list
tn orgs members       list | set-role <email> <papel> | remove <email>
tn orgs invitations   list | create EMAIL... --role <papel> | resend <email> | revoke <email>
tn orgs api-keys      create --name <nome> [--role] [--expires-in-days N | --no-expiry] [--mint-only]
                      | list | revoke <id>
tn orgs devices       list | revoke <id>
tn catalogs     list [--q <texto>] | get <catalogo> | create --name <nome> [--slug] [--visibility]
                | update <catalogo> [--name] [--slug] [--visibility] | delete <catalogo>
tn datasources  list <catalogo> | get <catalogo> <fonte> | delete <catalogo> <fonte>
tn uploads      create <catalogo> <arquivo> [--wait] | list <catalogo>
                | get <catalogo> <id> [--wait] | delete <catalogo> <id>
tn projects     list [--q <texto>] [--survey <formulario>] | get <projeto>
                | create --name <nome> [--slug] [--kind] [--description] [--deadline]
                  [--requires-review] [--area <arquivo>]
                | update <projeto> [--name] [--slug] [--kind] [--description]
                  [--deadline | --clear-deadline] [--requires-review | --no-requires-review]
                  [--area <arquivo> | --clear-area]
                | start <projeto> | finish <projeto> [--note <texto>]
                | reopen <projeto> [--note <texto>] [--deadline <data>]
                | archive <projeto>
                | stats <projeto> [--tz] | team <projeto> [--tz]
                | daily <projeto> (--days N | --all) [--collector <pessoa>] [--tz]
tn projects members   list <projeto> | add <projeto> <pessoa> --role <papel-no-projeto>
                      | set-role <projeto> <pessoa> <papel-no-projeto> | remove <projeto> <pessoa>
tn projects layers    list <projeto>
                      | add <projeto> --catalog <catalogo> --datasource <fonte>
                        [--name <nome>] [--style <estilo>] [--order N]
                      | remove <projeto> --catalog <catalogo> --datasource <fonte> [--name <nome>]
tn projects surveys   list <projeto>
                      | add <projeto> <formulario> [--area <arquivo>] [--participant <pessoa>]...
                      | remove <projeto> <formulario>
tn projects bundles   list <projeto> | retry <projeto>
tn projects events    list <projeto> [filtros] | summary <projeto> [filtros]
                      | export <projeto> -o <arquivo.csv> [--force] [filtros]
tn projects responses list <projeto> [--state] [--q] [--collector] [--survey]
                      | summary <projeto> [--q] [--collector] [--survey]
                      | get <projeto> <coleta>
                      | review <projeto> COLETA... (--approve | --reject | --reopen) [--comment]

<papel> é sempre owner, editor ou field, o papel na organização. <papel-no-projeto> é manager (gestor), collector (coletor) ou reviewer (revisor). <pessoa> é o e-mail ou o id de um membro.

Não existem comandos para criar ou editar formulários, nem para integrações: tn projects surveys só coloca e tira de um projeto formulários que já existem.

Membros e convites¶

tn orgs members set-role ana@exemplo.com editor
tn orgs members remove ana@exemplo.com
tn orgs invitations create ana@exemplo.com beto@exemplo.com --role field
tn orgs invitations resend ana@exemplo.com

invitations create imprime uma linha por endereço. Um endereço que não pode ser convidado (já é membro, por exemplo) não impede os outros, mas o comando termina com código 1 se algum falhou. list mostra só convites pendentes e dentro da validade; para renovar um convite expirado, convide o endereço de novo. As regras de papel, remoção e do último Gestor estão em Membros e convites.

Chaves de API e dispositivos¶

tn orgs api-keys create --name "ci-pipeline" --role editor --mint-only
tn orgs api-keys revoke <id-da-chave>
tn orgs devices revoke <id-do-dispositivo>

create imprime o segredo uma única vez. Por padrão, --role é editor e a validade é 365 dias (--expires-in-days, até 3650; --no-expiry para nunca expirar).

Criar uma chave troca o seu login local

Sem --mint-only, tn orgs api-keys create substitui o token guardado nesta máquina pela chave recém-criada: a partir daí o tn age como a chave, não como você. Use --mint-only quando a chave for para outro lugar (CI, outro servidor) e você quiser continuar logado aqui. No destino, defina TN_TOKEN e TN_ORG.

Catálogos¶

tn catalogs create --name "Limites de campo" --visibility private
tn catalogs update limites-de-campo --name "Novo nome" --slug novo-slug
tn catalogs delete limites-de-campo

O slug é gerado a partir do nome quando você não passa --slug. --visibility aceita private (padrão) ou public; o que cada visibilidade significa está em Catálogos e fontes de dados.

Envios e fontes de dados¶

tn uploads create limites-de-campo ./estradas.geojson --wait
tn uploads get limites-de-campo <id-do-envio> --wait
tn datasources list limites-de-campo
tn datasources get limites-de-campo estradas

uploads create envia o arquivo direto para o armazenamento e volta assim que o envio é criado; o processamento que o transforma em uma ou mais fontes de dados acontece no servidor. Com --wait (em create ou em get) o tn consulta o status a cada 2 segundos e espera até 5 minutos pelo resultado (ready ou failed); passado esse tempo, ele desiste com erro, mas o processamento continua e você pode consultar depois com get. Um envio só pode ser excluído enquanto está pendente ou falhou. Formatos aceitos, limites e erros de processamento estão em Importar dados.

Fontes de dados nunca são criadas ou editadas pelo tn: elas nascem de um envio concluído. datasources delete remove a fonte e seus dados.

Projetos¶

tn projects create --name "Obra BR-101" --deadline 2026-12-31 --requires-review \
  --area ./trecho.geojson
tn projects update obra-br101 --name "Obra BR-101 (lote 2)" --clear-deadline
tn projects get obra-br101
tn projects archive obra-br101

Um projeto criado pelo tn nasce em rascunho. O status muda só por três comandos, os mesmos passos do web app (veja Concluir e reabrir):

tn projects start obra-br101
tn projects finish obra-br101 --note "Campanha encerrada"
tn projects reopen obra-br101 --deadline 2026-12-15

start coloca um rascunho em andamento e exige a área. finish conclui um projeto em andamento e avisa a equipe por e-mail; reopen o reabre, com um novo prazo se você passar --deadline. Pedir um passo fora de ordem (concluir um rascunho, por exemplo) falha com a mensagem da API. update não muda o status. update muda só os campos que você passa; --clear-deadline e --clear-area apagam o prazo e a área. get mostra os campos do projeto e, em tabelas separadas, suas camadas (a de cima primeiro, como na lista de camadas do mapa), seus formulários e sua equipe. Com --json, as camadas vêm na ordem da API, de baixo para cima.

--area lê um arquivo GeoJSON com um único Polygon ou MultiPolygon: a geometria sozinha, uma Feature ou uma FeatureCollection com exatamente uma Feature. Qualquer outra coisa (um ponto, duas feições, um arquivo que não é GeoJSON) é recusada antes de chegar à API. As coordenadas são em WGS 84, como manda o GeoJSON. Shapefile, KML e áreas com várias partes separadas só pelo web app, que converte e une os arquivos. As regras de tamanho e validade da área são as mesmas do web app.

Equipe do projeto¶

tn projects members list obra-br101
tn projects members add obra-br101 ana@exemplo.com --role collector
tn projects members set-role obra-br101 ana@exemplo.com reviewer
tn projects members remove obra-br101 joao@exemplo.com

Cada comando muda uma pessoa e deixa o resto da equipe como está. A pessoa é indicada pelo e-mail (maiúsculas e minúsculas não importam) ou pelo id, e precisa ser um membro ativo da organização. Adicionar quem já está na equipe é recusado; para mudar o papel, use set-role. O criador do projeto continua gestor: mudar o papel dele ou removê-lo é recusado. Quem deixa de ser coletor, por troca de papel ou remoção, sai também dos formulários em que coletava.

members muda a equipe; team (abaixo) mostra a situação de campo dela. Os papéis estão em Papéis e permissões.

Camadas do projeto¶

tn projects layers list obra-br101
tn projects layers add obra-br101 --catalog dnit --datasource rodovias
tn projects layers add obra-br101 --catalog dnit --datasource pontes --name "Pontes" \
  --style pontes-por-tipo --order 5
tn projects layers remove obra-br101 --catalog dnit --datasource rodovias
tn projects layers remove obra-br101 --catalog dnit --datasource lotes --name "Lotes livres"

layers list mostra as camadas na ordem do mapa: a de cima primeiro. Com --json, elas vêm na ordem da API, de baixo para cima.

layers add desenha uma fonte de dados no mapa do projeto. Sem --name, a camada leva o nome da fonte; sem --style, usa o estilo padrão dela. A ordem de desenho é um número, e a camada de número maior fica por cima. Sem --order, a camada vai para o topo, acima de todas as outras. Com --order N, ela fica exatamente nesse número, mesmo repetindo o de outra camada, e nenhuma outra camada muda de lugar. Os números não precisam ser seguidos. O nome de cada camada é único no projeto, e um estilo feito para outro tipo de geometria é recusado.

layers remove identifica a camada pela fonte de dados que ela desenha (--catalog e --datasource). Se o projeto tem duas camadas da mesma fonte, por exemplo "Lotes vendidos" e "Lotes livres", o comando não remove nenhuma, lista as duas e pede --name para escolher.

Uma camada não é editada no lugar. Para trocar o nome, o estilo ou a ordem, remova e adicione de novo. A camada volta como nova (com outro id) e, sem --order, vai para o topo.

Formulários do projeto¶

tn projects surveys list obra-br101
tn projects surveys add obra-br101 rdo-dnit097
tn projects surveys add obra-br101 vistoria-ponte --area ./trecho-sul.geojson \
  --participant ana@exemplo.com --participant joao@exemplo.com
tn projects surveys remove obra-br101 vistoria-ponte

surveys add coloca um formulário da organização no projeto. --area restringe onde ele é coletado e segue as mesmas regras do --area de projects create. --participant, repetido para cada pessoa, indica quem coleta nele: o e-mail ou o id de um coletor do projeto (adicione a pessoa antes com members add --role collector). Um formulário entra uma vez só em cada projeto.

surveys remove tira o formulário do projeto junto com os participantes. As coletas já feitas nele continuam no projeto.

Um formulário do projeto não é editado no lugar. Para trocar a área ou os participantes, remova e adicione de novo, passando outra vez os participantes: eles não voltam sozinhos.

Pacotes e visão geral¶

tn projects bundles list obra-br101
tn projects bundles retry obra-br101
tn projects stats obra-br101
tn projects daily obra-br101 --days 14 --collector ana@exemplo.com
tn projects team obra-br101

bundles list mostra as versões recentes do pacote offline, da mais nova para a mais antiga, e marca na coluna field a versão que o app recebe. bundles retry é o Verificar agora da aba Pacotes: verifica o pacote sem esperar os 2 minutos e diz quando a verificação acontece. Só funciona em projeto em andamento com área. O tn não baixa pacotes: um pacote é entregue a um dispositivo cadastrado, e o tn não é um. Como o pacote é gerado está em Pacotes offline.

stats, daily e team são os números da Visão Geral do projeto: o total de coletas, os dias com coleta, o melhor dia e a sequência atual; as coletas por dia (--days N para os últimos N dias, --all desde a primeira); e, para cada coletor, se tem o pacote, a última sincronização e as coletas de hoje e do total. team mostra a situação de campo; ele não muda a equipe do projeto. --collector aceita o e-mail ou o id da pessoa. Os dias são contados no fuso de --tz (por exemplo America/Manaus); sem ele, no de Brasília (America/Sao_Paulo). O que conta como coleta está em Acompanhar o projeto.

Atividade¶

tn projects events list obra-br101 --kind response_rejected --from 2026-10-01 --to 2026-10-23
tn projects events list obra-br101 --person ana@exemplo.com --person terranode --period 7d
tn projects events summary obra-br101 --period 30d
tn projects events export obra-br101 --period 30d -o atividade.csv

São os eventos da aba Atividade, do mais recente para o mais antigo. list, summary e export aceitam os mesmos filtros:

Filtro O que faz
--q <texto> Procura no título, na descrição, na pessoa, no aparelho e no tipo
--person <pessoa> E-mail ou id da pessoa; terranode para os eventos do sistema. Pode repetir
--kind <tipo> Tipo do evento, como response_collected ou member_added. Pode repetir
--period 24h\|7d\|30d As últimas 24 horas, 7 dias ou 30 dias
--from <data>, --to <data> Um intervalo de dias, inclusive, no fuso de --tz
--tz <fuso> Fuso dos dias; sem ele, America/Sao_Paulo

Os tipos são os da tabela em Acompanhar o projeto; com tn --json projects events list cada evento traz o seu kind. Uma pessoa que saiu da organização continua nos eventos e pode ser filtrada pelo e-mail. Um e-mail que nenhum membro da organização tem é um erro, não uma lista vazia.

Quem não é gestor ou editor da organização, nem gerencia o projeto, vê os eventos de gestão e só os próprios eventos de campo, como no web app. list lê todas as páginas a partir do mesmo instante, então eventos que chegam durante a leitura não se repetem nem deslocam a lista.

summary mostra o total do resultado, as contagens por tipo e por pessoa e o total dos últimos 30 dias sem filtro. export grava o CSV da aba Atividade (UTF-8 com BOM, mesmas colunas) no arquivo de -o; ele se recusa a sobrescrever um arquivo que já existe, a menos que você passe --force.

Coletas e revisão¶

tn projects responses list obra-br101 --state pending --survey rdo-dnit097
tn projects responses summary obra-br101 --collector ana@exemplo.com
tn projects responses get obra-br101 RDO-DNIT097-00139
tn projects responses review obra-br101 RDO-DNIT097-00139 RDO-DNIT097-00140 --approve
tn projects responses review obra-br101 RDO-DNIT097-00141 --reject --comment "Foto ilegível"

list mostra as coletas da mais recente para a mais antiga pela primeira chegada, com número, estado, formulário, coletor e chegada. Os estados são approved (aprovada), pending (aguardando revisão) e rejected (rejeitada). --state, --collector e --survey podem se repetir; --collector aceita o e-mail ou o id da pessoa, e --q procura no número e no nome do coletor. summary conta as coletas por estado, com os mesmos filtros. get mostra uma coleta com as respostas, as mídias e o histórico de chegadas e revisões; o link de cada mídia expira e só sai com --json.

review decide uma ou mais coletas de uma vez: --approve aprova, --reject rejeita (pede --comment, que o coletor vê) e --reopen devolve a coleta para revisão. Só funciona em projeto que exige revisão, para quem é gestor ou revisor do projeto, e ninguém revisa a própria coleta. O tn lê cada coleta antes de decidir e decide sobre o estado que leu. O comando imprime uma linha por coleta, com um destes resultados:

Resultado O que significa
decided A decisão foi registrada
conflict A coleta mudou depois da leitura (outra pessoa decidiu, ou chegou uma nova versão do campo) e ficou como estava. Rode o comando de novo para decidir sobre o estado atual
own_collection A coleta é sua, e você não pode revisá-la
not_found Nenhuma coleta do projeto tem esse número ou id

As outras coletas são decididas mesmo quando uma falha, mas o comando termina com código 1 se alguma não foi decidida.
